# 公众号写作机制与 API 初稿执行

2026-10-06 用户明确纠正：网页内 API 扩写初稿为主路径；外部 AI 是可选出口。UI 当前方向认可，重点转向底层写作机制。本文覆盖产品机制、当前代码差距和可执行入口，不能把机制稿当成部署完成。

## 1. 用可复用规则组织写作

“像 skill 一样”指应用内部的版本化写作规则，不需要先安装 Codex skill 或引入自主 Agent 框架。资料、文章类型、骨架、个人风格和本文观点分开；用户选题与观点决定不交给模型代替。规则优先级：事实依据与边界 → 确认意图和大纲 → 用户风格 → 默认文风。

首版交互主路径：选定热点 → AI 读取资料并提出具体大纲 → 用户改骨架/要点并确认 → API 扩写初稿 → 用户编辑与必要的 AI 修改 → 审校 → 配图排版预览。资料读取和质量检查由系统完成，不增加一堆“等待查看”页面。仅选题、文章意图/大纲、最终成品等真正需要判断之处由用户决定。

## 2. 各阶段输入、输出与返工规则

| 阶段 | 输入 | 输出与责任 |
| --- | --- | --- |
| 阅读资料 | 选题、原始与补充 URL、用户粘贴资料 | 原文/明确摘录、来源 ID、读取状态；链接不等于已读全文，摘要不冒充事实证据 |
| 材料整理 | 原始正文、用户想法 | 核心事实及引用位置、时间范围、矛盾与缺口；用户批注不当作事实 |
| 策划 | 文章类型、读者问题、骨架、材料 | 各段作用、具体内容、来源依据、承接、阅读收获；建议可编辑，不替用户决定立场 |
| 确认快照 | 用户修改后的策划 | 保存完整结构、来源与写作规则版本；之后资料/大纲变化使旧生成和审校过期 |
| 扩写初稿 | 确认快照、偏好、正文证据 | Markdown 正文、资料缺口、段落覆盖；用具体内容扩写，不仅换说法或堆新闻 |
| 审校 | 初稿、确认意图、原始材料 | 事实/结构/文字/用户意图四类具体问题、定位与修改建议；模型自评不代表质量通过 |
| 修改 | 当前版本、明确范围、意见 | 保留未涉及内容，局部或全文修改可选择；换主线时回策划，旧稿保留 |
| 发布准备 | 用户认可的正文 | 配图、绿色排版、手机预览、复制；实际图片与排版另行落实 |

材料不支持关键主线时返回具体缺口，先补资料/收窄策划。局部资料不足可合理收窄，并说明缺口；不能以过度免责声明掩饰错误。生成成功即保留草稿，审校失败也不丢稿。避免无上限自动重写：首轮初稿与一次审校，必要修改由明确问题或用户意见触发。

## 3. 三种文章类型不能共用一个硬观点规则

- 事件介绍：发生了什么、哪里有意思、必要背景、哪些变化仍待观察。允许解释型中心，无需作者表态。
- 解释分析：具体问题、概念/机制/比较维度、资料允许的认识，区分事实与推论。
- 方法分享：用户认可的主张、具体动作、理由、例子、适用边界与验证方式，禁止虚构个人经历。

骨架有标题与段落作用，但实际 keyPoint 要来自这篇材料和用户意见。风格尚未从样稿学习时采用清晰、具体、克制的默认风格；不假装已掌握用户个人风格。当前两套/类型骨架仅为讨论原型，国内高关注样本研究仍待开展。

## 4. 当前代码诊断

main 存在模型 API 与已确认策划生成机制，但新版页面原型尚未接入。PR #2（fix/editorial-quality）已有事实/结构/文字审校和自然语言修稿，但尚未合并、部署或真实验收。

PR #2 的 `editorialBrief()` 要求所有题材给出 thesis，并将 readerQuestion、thesis、段落字段压入 angle/outline 字符串。此设计便于旧页面兼容，却不够支持明确的文章类型、骨架身份、用户观点和逐段证据检查。后续应保留结构化快照，不只靠提示词里的标题组织。API `tasks.start` 当前还未传递文章类型等新契约，所以新原型不能假装直接调用旧接口就已经实现这些机制。

完整接入还需要：项目数据保留新策划契约，cloud-api 校验并保存，任务消费确认快照，前端把扩写作为主要动作，审校与版本失效贯通。不能只把旧复制按钮改名为“生成初稿”。

## 5. 本轮可执行基础与边界

新增 `src/writing-policy.js`：版本化生成/审校规则，三类文章分支，结构化资料和段落输入，链接/来源 ID 校验，资料不足分支，审校问题定位，生成后的质量状态不自动称通过。新增 `scripts/generate-first-draft.mjs`：调用既有 createAI 真 API，保存初稿后再审校；不写数据库、不部署、不读取凭证文件，输出目录必须为新目录。

这是独立执行/评估入口，尚未整合进生产 `tasks.*`，也不包含 AI 策划、用户样稿学习或生图。规则约束和程序校验仍不能保证语义正确；需要看实际文章。不要将这些新文件描述成完整产品工作流已经实现。

运行要求：已有安全配置的模型运行环境，`WRITTER_AI_KEY`、现有 base URL/model 配置；不需要在聊天、仓库或前端提供密钥。当前会话没有 CloudBase 调用能力、本地无 WRITTER_AI_KEY，所以真实 API 初稿仍未执行。没有绕过鉴权或拿助手手写文章充当 API 结果。

```sh
node scripts/generate-first-draft.mjs /安全位置/confirmed-brief.json /安全位置/new-draft-output
```

输入契约示例（选题、大纲及原文由实际确认内容填写）：

```json
{
  "articleType": "event",
  "title": "实际文章标题",
  "reader": "目标读者",
  "readerQuestion": "本文要帮助读者弄明白什么",
  "authorNotes": "用户的想法或批注，不能自动当作事实",
  "stylePreferences": "当前确认的表达偏好",
  "documents": [{"id":"source-1","name":"来源名称","url":"https://实际原文地址","text":"已读取原文或明确摘录"}],
  "sections": [
    {"title":"开篇","purpose":"交代事情与问题","keyPoint":"实际确认的具体内容","sourceIds":["source-1"],"transition":"接着解释哪个变化"},
    {"title":"展开与收束","purpose":"解释并回应问题","keyPoint":"实际确认的具体内容","sourceIds":["source-1"],"transition":"回到读者的疑问"}
  ]
}
```

方法类额外需要 authorPosition（用户认可的主张）。输入必须从确认快照构建；这个 CLI 自身不会证明用户真的确认过。资料最长总计 60000 字符，1–5 份，每份 30000；超限先选择相关原文摘录，不静默截断。大纲 2–8 部分。写作记录保存在新输出目录，不自动公开上游正文。

## 6. 云端执行交接

在本地 Codex 已授权的 Writter 上海环境中：先读接续指南与本文件，核对 PR/模型状态；按明确任务接入结构化快照与以上规则；仅更新函数代码与必要 hosting，保留环境变量和鉴权，不用 `deploy --force` 覆盖密钥；用同一份真实资料、用户确认大纲生成一次初稿和审校，并把去敏正文与具体质量观察交付。不要复制云端密钥到聊天或为了跑 CLI 将密钥导出到普通文件。若以安全云端运行环境执行独立入口，遵循原有凭证管理。

首个真实成品检查：事件是否说清、要点有无实质展开、段落是否推进、标题/结尾是否越过资料、语言是否空泛、方法主张是否属于用户。分别记录服务连通、执行成功、内容质量与页面体验，不能合并成“全部通过”。
